## 讨论 1（2026-09-06）· 读摘要 —— 核心 claim

### 你的理解
> "相比较 ReTool 用于 text 推理强化，ReTool 在数学竞赛题上的推理强化可以用更少轮次得到更好的训练效果吗？"

### 结论：方向对 ✅，但概念要拆开

摘要对比的**不是"ReTool 用在数学 vs 别处"**，而是**两种 RL 训练设置**：
- **纯文本 RL（text-based RL）**：RL 中模型只能自己推理，不能碰工具。
- **ReTool = RL + 代码工具（tool-augmented RL）**：RL 中模型可以调用 Python 解释器，看到执行结果再继续。

### 关键数字（Qwen2.5-32B）

| | 纯文本 RL | ReTool（RL+工具） |
|---|---|---|
| AIME 2024 | 40.0% | **67.0%** |
| AIME 2025 | 36.7% | **49.3%** |
| 收敛训练步 | 1080 | **400** |
| 回答长度 | 长 | 缩短 ~40% |

→ **两个"又"字要记住：又准（+27 点）又快（不到一半步数）。**

### 重要概念：摘要里有两个"轮次"

| | 英文 | 含义 | 对应数字 |
|---|---|---|---|
| 训练步 | training step | 一次梯度更新 | 400 vs 1080 |
| 交互轮 | turn/round | 一道题内模型↔工具来回几次 | ReTool 一道题内可多轮调工具 |

ReTool 是"一道题内**多轮**调工具"→ 换来"整体**更少训练步**"。两个"轮"别混。

### 为什么工具"又准又快"（三个机理）

1. **计算外包**：语言模型擅长推理思路、不擅长精确计算 → 工具消除"算错"丢分。
2. **执行反馈 = 样本内即时反馈**：纯文本 RL 只在结尾拿一个稀疏的 0/1；ReTool 每调一次工具立刻看到"成功/报错"，可在**同一次回答内纠错**。
3. **信号更干净 → 梯度更有效**：reward 更能反映"策略好坏"，每步更新更值钱 → 更少步收敛。

### 类比（固化用）
模型=学生，工具=计算器，RL=只判最终卷面分 0/1 的老师。

## 讨论 2（2026-09-06）· 读 Introduction —— ReTool 的定义与两个反馈环

### 你的理解
> "ReTool 的定义是模型解决数学问题需要调 tool；RL 的作用是观察调用 tool 的轨迹和最终结果，反馈回来用于自我修正和下次调用的增强。"

### 修正：你揉合了两个**不同的反馈环**

**① 样本内反馈环（环境回路）—— 每次推理都有，与"训练"无关**
```
模型说理 → 调工具 → 沙箱执行 → 返回"结果/报错"
     ↑                          │
     └──── 看到反馈，当场自我修正 ←┘
```
→ 这一步让**自我修正**发生（一次做题内就能改）。SFT 之后模型会格式就能享受这个环，**不需要 RL**。

**② 跨样本学习环（RL 回路）—— 这才是"训练"**
```
整道题走完 → 最终答案 → 规则奖励判分 (+1/0/-1)
     ↑                          │
     └──── 更新模型权重，让"好策略"更可能 ←┘
```
→ 这一步让**下次调用更强**（跨许多道题累积）。

### 表格：逐句纠正

| 你的说法 | 精确版本 |
|---|---|
| 需要调 tool | 模型**可选择**调 tool；学的是**strategic（何时该调）**——标题关键词 |
| RL 观察轨迹和结果 | 观察轨迹不是 RL 独有（SFT 也看轨迹但只是模仿）；RL 特有的动作是**用最终对错更新权重** |
| 反馈用于自我修正 | 自我修正由**样本内环**（执行反馈）完成，**在 RL 更新前就发生** |
| 用于下次调用增强 | "增强"才是 RL 的活：**最终得分 → 权重更新**，跨样本累积 |

### ⚠️ 最容易踩的误区
**ReTool 的奖励只判最终答案对错**（`\boxed{}` 提取 + 规则比对），**不是每调一次工具就给分**。工具执行的中间结果只是给模型看的上下文（帮当场纠错），**不直接产生训练信号**。

### 一句话定义（修正版）
> ReTool 训练模型做数学题时能按需调用代码工具；SFT 让它先学会"怎么调"，RL 则只根据最终答案对错给分，跨样本地强化"该调时调、报错会改"的策略——最终学会一个**自己决定何时用工具**的解题智能体。

### SFT vs RL 的分工（重要）
- **SFT（ReTool-SFT）**：教"会不会调" —— 学会工具调用**格式**（模仿）。
- **RL（Tool-augmented RL）**：教"该不该调" —— 学**策略/时机**（试错 + 打分）。

### 类比（固化用）
- SFT = 老师示范按键顺序，学生模仿。
- 样本内反馈 = 计算器报"语法错误"，当场重按（无需训练）。
- RL = 老师只打卷面分，一百次后学生悟出"哪些题型该用计算器" → 策略变化 = 权重更新。

- [ ] 论文里的图是否分**两个层次**：agent 循环（模型↔工具）+ 训练循环（权重更新）
- [ ] "strategic" 一词在 Intro 里怎么被论证（为什么工具不是每次都用）

## 讨论 3（2026-09-06）· 读 Methodology —— ReTool-SFT 数据怎么构造

### 你的理解
> "构造数据集的 prompt 是：先让 AI 给一个纯文字推理的 CoT（含计算步骤和结果），然后构造 code snippet 替换计算步骤，再沙盒执行得到结果回填作为 CoT 的一部分，推出结果作为 revised form。"

### 结论：基本正确（~90%）✅，需补 3 个细节

**准确流程是四步**（ReTool 论文 2.2 节 + Figure 8）：
```
① D_init：收集开源数学推理(Open-Thoughts) → 人类专家 + DeepSeek-R1 双重过滤 → 高质量纯文字 CoT
② 改写：Figure 8 prompt 把纯文字 CoT 改写成代码增强版
   → 只把"能用代码受益的笔算步骤"换成 <code>代码</code> + 解释器结果
   → 核心推理逻辑（含失败的尝试）保持不变 → Revised Thinking Process
③ 两阶段验证：格式验证（标签规范）→ 答案验证（最终答案==标准答案）
④ 得到 D_CI → 拿去 SFT
```

### 三个修正点

| # | 你的理解 | 修正 |
|---|---|---|
| ① | 原始 CoT 由 AI 生成 | 原始 CoT 来自**已精筛的数据集 D_init**（双重过滤），改写模型拿到现成的再 revises，不现场从头生成 |
| ② | 替换计算步骤 | 是**选择性**替换：只换"用代码能受益"的步骤；**失败的尝试也保留**（让 SFT 数据像真实做题，匹配 RL 的犯错-纠错形态） |
| ③ | 沙盒执行回填 | 分清两个执行场合：**数据构造时**解释器结果多为改写模型 inline 预测 + 验证兜底（Figure 8 第 5/6 条约束"必须 print""结果必须完全一致"）；**RL rollout 时**才是沙盒**真实实时**执行回填（2.3.1，见 `</code>` 触发→填 `<interpreter>`→继续生成） |

- 选择性替换+保留失败："replacing manual calculation steps that can benefit from code execution" + "including any unsuccessful attempts, should remain unchanged"

## 讨论 4（2026-09-06）· 追问数据过滤 —— "保留弯路"和"答案不一致就删"矛盾吗？

### 你的问题
> "如果失败走弯路的也保留，得到的答案大概率是错的；但答案不一致会被删掉——那走弯路的过程不也被删了、进不了 SFT 吗？"

### 结论：不矛盾 —— "失败"分两个层级
| | 范围 | 是什么 | 是否删除 |
|---|---|---|---|
| 过程性失败（弯路/死胡同/算错被当场纠正） | 轨迹内部 | 中途此路不通、心算错一次、试了笨办法，但**最终答案对**（纠回来了） | ❌ 保留 |
| 结果性失败（整题做错） | 整条轨迹 | 一路走错，**最终答案错** | ✅ 答案验证删除 |

`保留 unsuccessful attempts` = 第一种；`最终答案不一致就删` = 只针对第二种。**两者作用范围不同，不冲突。**

### 合起来的真实含义
> **保留"走弯路但最终纠对"的样本；删掉"走弯路且最终做错"的样本。**

### 为什么这样设计（深层用意）
SFT 要教 RL 学会"代码自我纠错"，就必须给模型看"犯错→发现→纠正"的活样本。若 SFT 全是完美解答，模型没见过错误长什么样，RL 时学不会纠错。**保留弯路 = 提供"从错误恢复"的示范**。

### 值得回论文深挖的细节（提示）
改写 prompt 第 6 条"执行结果必须和模型写的完全一致"→ 若原始 CoT 有**潜伏的算错中间步骤**（模型自己没察觉），换成代码算出正确结果后会与周边文字冲突 → 很可能在一致性/格式验证被筛。**活下来的多是"错误已被明示并纠正"的干净弯路**——这也是 D_CI 规模小的原因（过滤狠）。

### 消融 = 逐级分解图（32B-Instruct, AIME24）
